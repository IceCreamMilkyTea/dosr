# DOSR — Evaluation

This document defines the metrics and experiments, states the assumptions
behind every number, and discusses the results in
[eval/results/SUMMARY.md](../eval/results/SUMMARY.md) (generated by
`eval/plot.py` from the raw JSON written by `dosr-bench`).

## 1. What we measure and why

The proposal committed to four quantities: end-to-end approval latency,
certificate generation/verification overhead, propagation latency as the
number of nodes grows, and cost savings relative to every node reviewing
independently. The submission of one change decomposes into phases, each timed
by the client (`client.Timeline`) or by the nodes (commit records):

```
Submit()
 ├─ prepare        closure check, tree diff, render canonical request        (client CPU)
 ├─ intent         ReviewIntent tx committed, nonce read back                (one consensus round trip; optional)
 ├─ attest         attestor call = upstream (the LLM) + attestation overhead (commit + sign + nonce log)
 ├─ present        open the attestation (hide the key), sign the AcceptCommit
 ├─ admit          broadcast → CheckTx answered                              (evidence verification at one node)
 └─ commit         admitted → decided at the client's node                   (consensus)
decided_first / decided_all   Submit start → first / last honest node durably committed the block (propagation)
```

| Metric | Definition | Source |
|---|---|---|
| **E2E latency** | `total`: Submit start → decision known to the client | client |
| **Certificate overhead** | `attest − upstream` (commit+sign+nonce) and `present`; receipt bytes | notary timing headers, client |
| **Verification cost** | CheckTx time of one AcceptCommit on a cold node, by change size | `bench.Verify` (in-process) |
| **Consensus/propagation** | `commit`, `decided_first`, `decided_all`; rounds per block | client + commit records |
| **Cost** | provider calls, estimated tokens (bytes/4) and USD (mock price table) per accepted change | mock provider accounting |
| **Waste under contention** | reviews per accepted change with *k* concurrent contributors | `bench.Contention` |
| **Grinding** | acceptance rate of a change the reviewer approves with probability *p*, with/without intents | `bench.Grinding` |
| **Behaviour under faults** | per-submission latency through crash / restart / partition / heal; invariants afterwards | `bench.Faults` |

## 2. Setup and assumptions (read before quoting any number)

* **One machine.** All validators are in-process CometBFT nodes on one Apple
  M-series laptop (8 cores, 16 GB). CPU contention between nodes is real and
  grows with *n*; absolute numbers are therefore pessimistic for large *n*.
* **Emulated network.** Every p2p link goes through a userspace proxy with
  one-way delay + 10 % jitter. Presets: `lan` 0.2 ms, `regional` 10 ms, `wan`
  a 5-region matrix with RTTs 70–220 ms (round numbers of the magnitude public
  inter-region dashboards report — assumed, not measured; see
  `pkg/testnet/netem.go`). Bandwidth is not limited.
* **Mock LLM.** `LatencyRealistic` is an *assumed* model: median TTFT 1.2 s
  (lognormal σ 0.4), 60 output tok/s, 50 µs per input token; ≈ 6.7 s for a
  300-token review of a 10k-token prompt. `LatencyFast` (~0.3 s) is used where
  provider latency is not what is being measured. Tokens are estimated as
  bytes/4; USD uses a fixed price table (`pkg/llm/model.go`). **No number in
  this evaluation says anything about a real provider's latency or price.**
* **Trusted-proxy attestor.** Attestation overhead is the cost of committing
  to and signing a transcript. A real TLSNotary MPC session would add seconds
  and tens of MB of traffic (literature review §02); that cost is *not* in our
  numbers.
* **Timeouts.** `default` = CometBFT defaults (propose 3 s, prevote/precommit
  1 s, commit 1 s). `fast` = propose 0.8 s, prevote/precommit 0.3 s, and
  proceed as soon as all precommits arrive (`skip_timeout_commit`). Under
  defaults a transaction waits, on average, half a block interval plus the
  fixed 1 s `timeout_commit`; the network's contribution is only visible with
  `fast`.
* **Repetitions.** 20 sequential submissions per configuration (10 for the
  large-bundle and end-to-end runs, 20 trials for grinding). Percentiles over
  accepted submissions. Single run per configuration — no confidence
  intervals; treat differences below ~10 % as noise.

## 3. Experiments

| # | Experiment (`dosr-bench -exp`) | Configurations |
|---|---|---|
| E1 | `verify` — validator verification cost vs change size | 1 KB … 1 MB changes, cold app, no cache |
| E2 | `consensus` — commit and propagation vs *n* and network | *n* ∈ {4, 7, 10} × {lan, regional, wan} × {default, fast} |
| E3 | `bundle` — commit latency vs bundle size | 1 KB … 1 MB, *n*=4, regional |
| E4 | `e2e` — full breakdown, DOSR vs baseline | {dosr, baseline} × {no latency, realistic}, *n*=4, wan, default timeouts |
| E5 | `contention` — *k* contributors on one branch | *k* ∈ {1, 2, 4, 8}, 4 changes each, fast LLM |
| E6 | `faults` — a submission stream through faults | kill/restart validator 3; partition 3|1 (client on minority, then majority); heal |
| E7 | `grinding` — resampling until approval | *p*=0.25, 12 tries max, {no intents, intents with MaxAttempts 3 + single-use nonces} |

**Baseline (E4).** "Every validator reviews": receipts are ignored; each
validator recomputes the canonical request and calls the provider itself
while forming its vote (`ProcessProposal`), rejecting the proposal if its
verdict is negative; a verdict is memoised per transaction per node. This is
the design DOSR replaces. It is non-deterministic by construction (validators
may disagree) and its LLM calls sit inside consensus timeouts.

## 4. Results

See the generated tables and figures in
[eval/results/SUMMARY.md](../eval/results/SUMMARY.md). The discussion below
refers to them.

### E1 — Verification cost is negligible next to consensus and the LLM

Verifying one `AcceptCommit` on a cold node (decode envelope + bundle, closure
check, tree diff, render the canonical request, verify the notary signature
and Merkle root, parse the verdict) costs **0.15 ms** for a 1 KB change and
**11 ms** for a 1 MB change (p50). Even at 1 MB it is 1 % of a block interval.
The evidence cache removes two of the three verifications per node in the
common path. Conclusion: *validators verify instead of review* costs
milliseconds; the review itself costs seconds and dollars.

### E2 — Consensus and propagation vs *n* and network

With CometBFT's default timeouts the latency from submission to a decided
block is **~1.3 s** for every configuration (4–10 validators, LAN to WAN),
because it is dominated by the fixed `timeout_commit` (1 s) plus half a block
interval of waiting; the network shows up only in the p90 (1.32 s LAN → 1.49 s
WAN at *n*=10). This matches the published Tendermint numbers (2.1–2.5 s block
latency on 16 AWS regions including the 1 s commit timeout, literature review
F9) in order of magnitude.

With `fast` timeouts the network becomes visible: `decided_all` p50 rises from
**0.64 s (4, LAN) to 1.18 s (10, WAN)**, and from 0.64 s to 0.75 s with *n* on
the LAN alone — the latter is CPU contention of 10 in-process nodes as much as
message complexity (Tendermint's O(*n*²) votes). No block needed more than one
round in any configuration.

### E3 — Bundle size

Carrying the bundle inside the transaction costs nothing measurable up to
100 KB and is within noise at 1 MB (commit p50 1.18–1.29 s, all within the
timeout-dominated regime); client-side preparation grows to 13 ms at 1 MB.
Gossiping a 1 MB transaction to 4 nodes on emulated links with unlimited
bandwidth is cheap; a bandwidth-limited WAN would change this, and so would
larger validator sets. The design keeps the option of ordering only a digest
plus an availability certificate for that regime.

### E4 — End-to-end: DOSR vs every-validator-reviews

| | DOSR | baseline |
|---|---|---|
| total p50, realistic LLM | **7.2 s** (6.5 s of which is the LLM call) | **29.7 s** |
| rounds per block | 1 | 5 |
| provider calls per accepted change | 1 | 4 (= *n*) |
| cost per accepted change (mock prices) | $0.0086 | $0.0344 |
| attestation overhead (commit + sign) | 1.2 ms | — |

Two things happen to the baseline. First, cost and calls scale with *n* by
construction. Second — and this is the systems point — a multi-second LLM call
inside `ProcessProposal` exceeds `timeout_propose` (3 s): every block needs
**5 rounds** before the validators' memoised verdicts let one succeed, so the
baseline is 4× slower than the LLM call itself, not merely 1×. With no LLM
latency the two designs are indistinguishable (1.3 s), which confirms that
DOSR's receipt verification adds nothing measurable on the consensus path.

The attestation overhead (1.2 ms) is that of the *trusted-proxy* attestor;
with MPC-TLS it would be seconds (literature review §02).

### E5 — Contention (and a bug it found)

Optimistic concurrency wastes reviews: with *k* contributors racing on one
head, at most one wins per block and the others have paid for a review they
must redo. Measured reviews per accepted change: **1.0 / 1.75 / 2.44 / 5.12**
for *k* = 1 / 2 / 4 / 8. Throughput is flat (~45 accepted/min, one per block)
— the branch is a serial resource.

The first run of this experiment gave **3.0 / 6.44 / 15.97**: a loser refused
at the mempool (the node's check state already held a competitor) re-reviewed
immediately although the chain head had not moved, and was refused again —
a busy loop of paid reviews until the next block (design log D13). The client
now waits for the head to actually move. Mitigations for the remaining,
inherent waste (leases on the head, Bors-style batching, rebase-tolerant
receipts) are future work.

### E6 — Faults

The stream of submissions continued through a validator crash (p50 unchanged
at 1.33 s; one submission took 5.5 s because the dead validator was the
proposer for a round), its restart (the node caught up and rejoined), and a
3|1 partition (majority side unaffected; the client attached to the isolated
node could not get anything decided within its 15 s deadline, as it must not).
After healing, the isolated node caught up and the invariant checker found all
four nodes in agreement with a certified, linear history.

### E7 — Grinding

For a change the reviewer approves with probability 0.25 and a contributor
willing to try 12 times, acceptance was **19/20** without intents (expected
0.97) at 3.85 reviews per trial. With intents (`MaxAttempts` 3) and single-use
nonces, acceptance was **13/20 = 0.65** (expected 1 − 0.75³ = 0.58; 20 trials,
binomial s.d. ≈ 0.11) at 2.2 reviews per trial; 7 trials were stopped by the
chain (`too_many_attempts`). The mechanism bounds grinding as designed; it
does not eliminate it, and its bound is per identity (DESIGN §4.6).


## 5. Demo

`bin/dosr-dev` starts a 4-validator chain, the mock provider and a notary on
localhost and prints the addresses; the `dosr` CLI then works against a real
Git repository (`create-repo` with a root commit, `submit` of a child commit,
`log`). The transcript in the checkpoint report was produced this way.
