# DOSR — Latency analysis

This note answers four questions about DOSR's latency with the numbers we
measured, says where each number comes from, and states the assumption behind
every number that depends on the LLM. Sources: `eval/results/SUMMARY.md`
(generated by `eval/plot.py` from `eval/results/raw/*.json`, written by
`dosr-bench`), `docs/EVALUATION.md` (setup), `docs/notes/impl_testnet.md` §6
(harness measurements), `eval/results/COST.md` (real-commit request sizes),
and the literature review (`docs/literature/02_*`, `03_*`).

**Setup common to every number below.** One Apple M-series laptop (8 cores,
16 GB); all validators and full nodes are in-process CometBFT v0.38 nodes;
every p2p link runs through a userspace proxy with a configured one-way delay
(+10 % jitter): `lan` 0.2 ms, `regional` 10 ms, `wan` a 5-region matrix with
RTTs 70–220 ms. Bandwidth is unlimited. The LLM is a mock whose latency is an
**assumed** model (`pkg/llm/model.go`, `LatencyRealistic`): time-to-first-token
lognormal with median 1.2 s (σ 0.4), 60 output tokens/s, 50 µs per input token,
tokens estimated as bytes/4, ~300 output tokens per review. The attestor is a
trusted proxy (no MPC-TLS). Single run per configuration; differences below
~10 % are noise. Nothing here is a measurement of a real provider.

## 1. How long does it take for a PR to be evaluated?

A submission goes through the phases timed by the client (`client.Timeline`)
and the nodes (commit records):

```
total ≈ T_prep + [T_intent] + T_llm(size) + T_attest + T_present + T_admit + T_consensus
```

| Term | What | Measured (p50) | Source | Assumption |
|---|---|---|---|---|
| `T_prep` | closure check, tree diff, render canonical request | 0.15 ms (2 KB); 0.08 / 0.28 / 1.8 / 6.8 ms for 1 KB / 10 KB / 100 KB / 1 MB | E4 `e2e_dosr_realistic`; `e2e_size` | none (client CPU) |
| `T_intent` | `ReviewIntent` tx committed and nonce read back, only if the policy requires intents | 380 ms with fast timeouts on an undelayed link (`grinding_intents_max3`, 13 accepted); ≈ one block ≈ **1.3 s** with default timeouts (consensus table, any *n*, any network) | E7, E2 | none |
| `T_llm` | the provider call as measured by the attestor | **6.5 s** for a 2 KB change (5.4 KB request ≈ 1.35k tokens) | E4 | assumed model: 1.2 + 300/60 + 1350×50 µs ≈ 6.3 s median |
| `T_attest` | attestor time minus upstream (commit to transcript, sign, nonce log) | **1.2 ms** (2 KB); 0.3 / 0.4 / 1.2 / 8.3 ms by size | E4; `e2e_size` | trusted proxy; MPC-TLS would be 3.6–14.5 s for a 1 KB request (literature §02, TLSNotary May-2026 benchmarks) and ~10 MB of upload per KB *sent* |
| `T_present` | open the attestation, sign the `AcceptCommit` | 0.14 ms | E4 raw | none |
| `T_admit` | broadcast → `CheckTx` answered | 0.7 ms (2 KB); 0.2 / 0.5 / 2.7 / 10.7 ms by size | E4 raw; `e2e_size` | none; the verification itself costs 0.15 ms (1 KB) to 11 ms (1 MB) cold (E1 `verify`) |
| `T_consensus` | admitted → decided at the client's node | **1.02 s** (E4); 0.56–1.0 s in `e2e_size`; **1.3 s** when the tx is submitted immediately after the previous block (E2, E3) | E4, E2, E3 | CometBFT default timeouts: `timeout_commit` 1 s |

**Measured instance (E4, DOSR, 4 validators, WAN, default timeouts, 2 KB
change, realistic LLM model):** `total` **p50 7.2 s, p90 8.2 s**, of which the
LLM call is 6.5 s, consensus 1.0 s, and everything DOSR adds on top of "call the
model and order a transaction" is **about 2 ms** (prepare + attest + present +
admit). With the LLM latency switched off the same pipeline takes 1.31 s, the
same as the "every validator reviews" baseline without LLM latency (1.31 s),
which confirms that receipt verification is not measurable on the consensus
path. With the realistic model the baseline takes **29.7 s** (its LLM calls sit
inside `ProcessProposal` and exceed `timeout_propose`, so every block needs 5
rounds) against DOSR's 7.2 s.

**How the LLM term grows with change size** (new experiment `e2e_size`: DOSR,
4 validators, WAN, default timeouts, `LatencyRealistic`, 6 submissions per
size; submissions 1–5 *add* a file of the given size, submission 6 *rewrites*
the file added first, so its diff has old and new lines and is ~2× larger —
that is where the p90 column and the above-average request bytes come from):

| change | request bytes (avg) | tx bytes | client prepare | LLM call p50 | attest overhead | admit | commit p50 | **total p50** | total p90 | decided_all p50 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 KB | 3 410 | 5 826 | 0.08 ms | 6.66 s | 0.3 ms | 0.2 ms | 1.00 s | **7.7 s** | 8.2 s | 7.7 s |
| 10 KB | 15 663 | 15 089 | 0.28 ms | 6.57 s | 0.4 ms | 0.5 ms | 0.96 s | **7.9 s** | 8.1 s | 8.0 s |
| 100 KB | 137 336 | 107 269 | 1.8 ms | 7.61 s | 1.2 ms | 2.7 ms | 0.56 s | **9.3 s** | 10.7 s | 9.3 s |
| 1 MB | 1 294 612 | 1 054 064 | 6.8 ms | 20.6 s | 8.3 ms | 10.7 ms | 0.66 s | **21.3 s** | 35.7 s | 21.3 s |

The per-sample values match the assumed model: a 1 MB *addition* renders to
1.11 MB of request ≈ 278k tokens → 1.2 + 5.0 + 13.9 ≈ 20.1 s (measured
20.1–20.9 s); the 1 MB *rewrite* renders to 2.2 MB ≈ 554k tokens → ≈ 34 s
(measured 33.9 s). Under this assumption the 50 µs/input-token term is
negligible below ~10 KB (0.2 s), equals the generation time at ~400 KB of
request, and dominates at 1 MB. Everything that is not the LLM stays within
~20 ms of its 1 KB value up to 1 MB: client preparation 6.8 ms, attestation
8.3 ms, admission 10.7 ms. Consensus commit does not grow with size (E3 and
this table); its p50 varies between 0.56 and 1.0 s here only because the
random LLM latency randomises the phase at which the transaction reaches the
mempool (see §2).

Where real PRs sit on this curve is in §4: the median rendered request of a
real CometBFT commit is 6.8 KB (2.6k tokens), the p99 70 KB (26k tokens), so
real reviews live between the 1 KB and 100 KB rows: **7–9 s end-to-end under
the assumed model**, of which 6.3–7.5 s is the model and ~1 s is consensus.

## 2. How long until an accepted commit is propagated on the blockchain?

Three measurements, all without LLM latency so that only consensus and the
network are visible.

**(a) First vs last validator (E2, `consensus_*`).** `decided_first` and
`decided_all` are the times from Submit start until the first / the last
honest node durably committed the deciding block (nodes' own commit
timestamps, one clock). Spread = `decided_all − decided_first`, from the raw
samples:

| configuration | decided_first p50 | decided_all p50 | spread p50 / max |
|---|---|---|---|
| 4 validators, LAN, fast | 639 ms | 645 ms | 9 / 18 ms |
| 4 validators, WAN, default | 1 246 ms | 1 312 ms | 67 / 103 ms |
| 4 validators, WAN, fast | 823 ms | 903 ms | 71 / 102 ms |
| 10 validators, WAN, fast | 1 109 ms | 1 196 ms | 99 / 137 ms |

The spread is of the order of one WAN one-way delay (35–110 ms in the preset):
the last validator is the one that receives the final precommit last. In the
E4 run with the realistic model the spread was 75 ms p50 / 110 ms max.

**(b) Non-validator full nodes (new experiment `propagation`).** 4 validators
plus {0, 2, 4} full nodes, `regional` (10 ms one-way), fast timeouts, 10
submissions each; per decided height we take every node's commit timestamp and
report spreads relative to the first validator. A full node is what a
`git clone` would talk to.

| full nodes | commit p50 | first validator | last validator | validator spread p50 / p90 / max | last full node | full-node spread p50 / p90 / max | **last full node after first validator** p50 / p90 / max | block interval (median) |
|---|---|---|---|---|---|---|---|---|
| 0 | 601 ms | 553 ms | 567 ms | 11.0 / 21.7 / 23.0 ms | – | – | – | 303 ms |
| 2 | 700 ms | 649 ms | 659 ms | 10.9 / 19.0 / 24.9 ms | 660 ms | 3.0 / 8.6 / 8.9 ms | **10.9 / 21.7 / 27.6 ms** | 385 ms |
| 4 | 784 ms | 737 ms | 753 ms | 15.0 / 28.0 / 115 ms | 753 ms | 12.2 / 17.0 / 19.1 ms | **15.8 / 25.1 / 115 ms** | 404 ms |

Full nodes have the block **within 11–16 ms (p50) of the first validator**, i.e.
one or two one-way delays, and essentially at the same time as the last
validator: a CometBFT full node follows consensus through the consensus
reactor (it receives the proposal and the votes like a validator) and commits
as soon as it holds the block and +2/3 precommits; it does not wait to be
served the block afterwards. The one 115 ms outlier (4 full nodes) hit both the
last validator and the last full node, so it is a late precommit, not a
full-node effect. What *does* grow with full nodes is the absolute commit
latency (601 → 700 → 784 ms) and the block interval (303 → 404 ms): six and
eight in-process nodes compete for the same 8 cores and gossip to more peers.
That is a cost of this harness, not of full nodes in a real deployment.

**(c) Block interval vs link delay (`impl_testnet.md` §6.1, 4 validators,
fast timeouts, `peer_gossip_sleep` 10 ms).** Median block interval 226 / 251 /
372 / 531 ms at 0 / 10 / 50 / 100 ms one-way delay, i.e. **about three
one-way delays per block** (proposal, prevotes, precommits each cross the
network once) plus a ~220 ms constant. Commit latency of one transaction is
bimodal at 100 ms: ~520 ms if it reaches the next proposer's mempool in time,
~1.1 s (one more height) if it does not; "about half" miss the next block at
100 ms of mempool-gossip delay. This is also why `commit` in §1 varies between
0.44 s and 1.9 s across individual samples (`e2e_size` raw).

**Durability semantics.** CometBFT has instant finality: a block is decided
when +2/3 of the voting power precommitted it, and under the BFT assumption
(< 1/3 faulty) it is never reorganised. The repository head on every honest
node is the head of the last decided block (`FinalizeBlock` is deterministic;
the invariant checker verified agreement on all nodes after every experiment,
including after the crash/partition sequence of E6). So `decided_first` is
*the* finality time; a `git clone` from any full node that has the block
returns a final head — there is no confirmation depth to wait for, and a
client reading from a node that is still catching up sees an older but
equally final head (restart catch-up: 141 ms to come up and 4.8 s for 9
blocks in-process, 3.2–3.4 s in subprocess mode, §6.3).

## 3. Comparison across network sizes

E2: *n* ∈ {4, 7, 10} validators × {lan, regional, wan} × {default, fast}
timeouts, 20 submissions each, 512-byte changes, no LLM latency.

**Default timeouts** (propose 3 s, prevote/precommit 1 s, commit 1 s) —
`decided_all` p50 / p90 (ms):

| *n* | lan | regional | wan |
|---|---|---|---|
| 4 | 1 268 / 1 288 | 1 271 / 1 285 | 1 302 / 1 401 |
| 7 | 1 267 / 1 292 | 1 264 / 1 308 | 1 334 / 1 428 |
| 10 | 1 226 / 1 282 | 1 285 / 1 325 | 1 423 / 1 476 |

**Fast timeouts** (propose 0.8 s, prevote/precommit 0.3 s, proceed as soon as
all precommits arrived) — `decided_all` p50 / p90 (ms):

| *n* | lan | regional | wan |
|---|---|---|---|
| 4 | 640 / 762 | 575 / 668 | 897 / 957 |
| 7 | 682 / 767 | 765 / 778 | 985 / 1 040 |
| 10 | 750 / 811 | 782 / 888 | 1 179 / 1 354 |

Every block was decided in round 0 in all 18 configurations.

*Why default timeouts hide the network.* After deciding height *h* a node
waits `timeout_commit` = 1 s before starting *h*+1; a transaction submitted
right after a decision (which is what the sequential harness does) therefore
waits ~1 s plus the ~0.3 s of the next round regardless of link delay. The
network only shows in the p90 and in the WAN column at *n*=10 (+0.15 s). The
published Tendermint numbers have the same structure: 2.14 s mean block
latency at 16 validators on 16 AWS regions, 2.53 s at 128, "includ[ing] an
artificial delay of 1 s, the timeout commit" (Cason et al., SRDS 2021,
literature review F9/§A.4) — an 8× larger validator set raised latency by 18 %.

*What fast timeouts reveal.* With the fixed wait removed, `decided_all` grows
from 0.64 s (4, LAN) to 1.18 s (10, WAN): **≈ +0.5 s from LAN to WAN at
*n*=10**, and +0.11 s from *n*=4 to *n*=10 on the LAN alone. The latter is as
much CPU contention of ten in-process nodes (and their 45 proxies) as the
O(*n*²) vote traffic — the block interval on the undelayed LAN grows from 341 to
388 ms with *n*, which a real deployment would not see. The WAN column at *n*=10
(1.18 s p50, 1.35 s p90) is where messages from the slowest region (110 ms
one-way) gate every step.

*Beyond what we ran.* We did not run more than 10 validators. For 16–128
validators over a real WAN the published figures above (2.1–2.5 s block
latency, 2.7–3.5 s transaction latency with default timeouts) are the best
available estimate; DOSR adds nothing to the consensus path (E4, no-latency
rows), so they transfer directly.

## 4. Comparison across prompt / conversation sizes

Three experiments separate the three places where size can hurt.

**Inside the transaction (E3 `bundle`, 4 validators, regional, default
timeouts, 10 submissions per size):** commit p50 1 287 / 1 287 / 1 260 /
1 183 ms for 1 KB / 10 KB / 100 KB / 1 MB changes (tx 5.8 KB … 1.05 MB);
client preparation 0.17 → 12.6 ms. **Flat up to 1 MB** on unlimited-bandwidth
links.

**At the validator (E1 `verify`, cold app, no cache):** 0.15 / 0.21 / 1.66 /
11.1 ms p50 (p90 0.39 / 0.72 / 2.4 / 15.3 ms) to verify one `AcceptCommit` of
1 KB / 10 KB / 100 KB / 1 MB. Even the 1 MB case is 1 % of a block interval,
and the evidence cache removes two of the three verifications per node.

**At the model (`e2e_size`, §1):** 6.7 → 6.6 → 7.6 → 20.6 s for the same
sizes under the assumed model. The whole size dependence of DOSR's latency is
the provider's input-token term; the protocol's own share grows from 0.5 ms to
26 ms (prepare + attest + admit) and consensus does not grow at all.

**Where real PRs sit.** From 398 rendered first-parent commits of CometBFT
(`eval/results/COST.md`; tokens measured with cl100k, 0.381 tokens/byte):

| statistic | files | +lines | request bytes | input tokens |
|---|---|---|---|---|
| p50 | 2 | 9 | 6 779 | 2 579 |
| p90 | 8 | 92 | 21 129 | 8 040 |
| p99 | 44 | 630 | 69 551 | 26 467 |
| max | 105 | 3 436 | 308 230 | 117 294 |

Under the assumed model the input term is 0.13 s at the median, 0.4 s at p90,
1.3 s at p99 and 5.9 s at the largest commit; end-to-end that is **≈ 7.5 s
(p50) to ≈ 8.7 s (p99) and ≈ 13 s (max)** with ~1 s of consensus — the
`e2e_size` rows 1 KB–100 KB bracket 99 % of real commits, and even the
largest real commit is a third of the 1 MB row. The 4 MiB `MaxDiffBytes` of
the policy is therefore not the binding limit for latency; the provider's
context window and price are.

**Multi-turn ("conversation") reviews — design reasoning only.** The
prototype makes exactly one non-streaming call per review (the literature
review recommends non-streaming because the attestation covers one request /
response pair). A review with *k* turns (e.g. ask for the diff summary, then
for the verdict, or let the model request more context) would cost
`Σ_i T_llm(size_i)` ≈ *k* × (ttft + output/rate) + 50 µs × Σ input tokens, and
since each turn re-sends the conversation so far, Σ input tokens grows
quadratically in *k* for a fixed per-turn addition. At the assumed parameters
a 3-turn review of a median commit is ≈ 3 × 6.3 s ≈ 19 s against 7.2 s, before
any attestation cost: every turn is a separate TLS exchange, so with MPC-TLS
each would add its 3.6–14.5 s and its ~25 MB fixed upload (literature §02).
Consensus is unaffected (one `AcceptCommit` carries one receipt per turn, or
one receipt over a multi-exchange transcript); the verifier cost grows with the
receipt, i.e. by milliseconds. The design keeps the number of turns a policy
parameter precisely because turns, not bytes, are what multiply latency and
attestation cost.

## 5. What would change in a real deployment

* **Real provider latency.** Every LLM-dependent number above assumes the
  `LatencyRealistic` model. A real provider's TTFT, generation rate, prompt
  processing and queueing (HTTP 529 under load, retries) replace the 6.3–7.5 s
  typical call with whatever that provider delivers; the *structure* (DOSR adds
  ~2 ms and one consensus round) does not change.
* **MPC-TLS attestation.** Replacing the trusted proxy by TLSNotary-style MPC
  would turn `T_attest` from ~1 ms into **3.6–14.5 s per call** (1 KB request,
  May-2026 benchmarks) plus ~10 MB of upload per KB of request — for the 6.8 KB
  median request that is of the order of 100 MB per review. Attestation would
  then rival the model call itself, and the diff size cap would be set by
  bandwidth, not by the model.
* **Bandwidth-limited links and more validators.** E3's flat curve relies on
  unlimited bandwidth; gossiping a 1 MB transaction to *n* validators over
  10–100 Mbit/s links costs 0.1–1 s per hop and multiplies with *n*. The
  design's fallback (order a digest plus an availability certificate instead
  of the bundle) exists for that regime.
* **Larger, geographically spread validator sets.** Expect the published
  2.1–2.5 s block latency for 16–128 validators with default timeouts; the
  O(*n*²) vote complexity only shows past ~100 validators in the literature.
  Our fast-timeout numbers are a lower bound and are inflated by CPU sharing
  for *n* ≥ 7.
* **Where the notary sits.** `T_attest` here is localhost. In production the
  contributor → notary → provider path adds two WAN legs (tens of ms each,
  plus TLS handshakes) and, for MPC, ~40 communication rounds between prover
  and notary — placing the notary near the provider's edge matters more than
  placing it near the contributor.
* **Clock and polling artefacts.** `decided_first` and `decided_all` share one
  clock here; across machines the spread measurement needs synchronised
  clocks, and the client's `total` includes ~20–40 ms of RPC polling that a
  subscription would remove.
